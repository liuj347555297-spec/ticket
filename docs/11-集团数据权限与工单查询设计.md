# 集团数据权限与工单查询设计

## 1. 目的与适用范围

本文冻结 ServiceHub 第一批 P0 的集团数据权限、工单查询、团队队列、分页和索引边界。目标是在一个集团平台内运营多个组织和多个服务系统时，任何集合查询都先在数据库中限定当前主体可见对象，再排序和分页；角色、前端菜单、请求参数或应用层事后过滤均不能替代数据隔离。

本批次采用“集团平台单实例域，组织/服务/队列/CI 为业务数据范围”的模型，不宣称具备可供互不信任外部客户共库使用的 SaaS 多租户能力。如未来需要法人或外部客户级强租户隔离，必须另行评审独立租户键、密钥、审计、备份恢复和物理拆分策略，不能把组织字段直接当作租户边界。

## 2. 不可信边界

- 浏览器、移动端、API 调用方不得提交或覆盖有效角色、授权组织、下级组织标志、服务范围、团队成员、队列范围、CI 范围、全局权限或授权版本。
- 查询中的组织、系统、目录、队列、状态、关键词和时间条件只是结果筛选，必须与服务端授权范围取交集；缺省筛选不表示全量。
- IAM 登录断言只证明不可变主体。平台角色、后台启用状态、数据范围和团队成员关系仍从服务端受控投影解析，并在每次领域操作重新确认。
- 工单历史身份、系统快照、路由快照和已完成任务只用于审计追溯，不能被用作当前授权证据。

## 3. 服务端授权上下文

每次请求或后台执行创建一个只读 `AuthorizationContext`。概念字段如下；具体 Java 类型由实现阶段确定，但语义不得缩减：

| 字段 | 含义 | 约束 |
| --- | --- | --- |
| `actorIamUserId` | 当前不可变 IAM 主体 | 只来自已验证登录或受管服务身份 |
| `actorActive` | IAM 当前活动状态 | 非活动主体安全拒绝 |
| `roleCodes` | 当前平台角色 | 只决定动作资格，不直接授予全量对象 |
| `organizationScopes` | 精确组织及显式包含下级的组织范围 | 下级集合由受控组织闭包解析 |
| `serviceScopes` | 服务系统或服务目录范围 | 使用稳定编码，不使用展示名称 |
| `queueScopes` | 团队队列范围 | 来自活动团队成员/显式授权 |
| `configurationItemScopes` | 受管 CI 范围 | 只来自 CMDB 投影和受控授权 |
| `globalBusinessScope` | 全集团业务对象范围 | 独立高危授权；任何角色都不隐含拥有 |
| `scopeVersion` | 当前有效授权事实版本摘要 | 用于游标失效、审计和缓存隔离 |
| `resolvedAt` | 上下文解析时间 | 不得长期缓存绕过撤权 |
| `action` | 本次读取、处理、审批、下载或导出动作 | 同一上下文不能跨动作提升权限 |

授权缓存如被采用，缓存键必须包含主体和范围版本；IAM 停用、后台授权、数据范围或团队成员变更必须使旧缓存失效。缓存不可用时回源受控投影，不能降级为宽角色权限。

## 4. 授权判定模型

### 4.1 基本公式

一次工单操作成功必须同时满足：

```text
主体活动
AND 动作角色允许
AND（直接对象关系允许 OR 显式数据范围命中 OR 独立全局业务范围允许）
AND 当前流程/任务/状态业务约束允许
```

同一授权包内，同类型多个范围值取并集，不同类型取交集；多个独立授权包之间才可取并集。这样“组织 A + 服务 B”只覆盖组织 A 内的服务 B，不会扩张为组织 A 全部服务与服务 B 全部组织。现有扁平 `platform_backoffice_user_data_scope` 在引入授权包主键前统一视为一个授权包；需要表达多组并集时必须先完成授权包数据模型和管理接口，不能由查询代码自行组合。实现还必须为每个动作声明允许使用的范围类型；平台配置管理员角色本身不授予工单读取，审计员只能在显式审计范围内只读。

### 4.2 直接对象关系

| 关系 | 最小能力 | 失效条件 |
| --- | --- | --- |
| 提单人 | 读取本人工单、补充允许内容、确认/重开等流程允许动作 | IAM 停用或流程不允许；不因此获得内部评论和管理字段 |
| 当前主办 | 在当前任务和状态允许时读取、处理 | 主办被替换、撤权、IAM 停用或任务结束 |
| 当前协办/有效代理 | 读取并完成被授权的协作动作 | 协办失效、代理到期、委托关系撤销或 IAM 停用 |
| 当前审批/确认任务受让人 | 读取审批所需最小摘要并提交本人任务 | Flowable 任务结束、撤销、重新指派或人员失效 |

直接关系不自动授予批量查询、报表、导出或跨工单搜索能力。团队主管或审计读取必须走显式范围授权。

第一批实现尚未交付可版本化、可撤销的“跨组织临时对象授权”持久化模型，因此采用更严格的兼容门禁：除提单人读取本人允许内容外，主办、协办、代理和审批参与关系不能单独绕过当前 `DATA_SCOPE`。参与人仍须具有当前有效角色并命中工单组织/系统/目录/CI 范围；否则列表、详情、附件和动作均安全拒绝。后续只有在临时对象授权具备授权来源、有效期、动作集合、撤销状态、范围版本和审计记录后，才能按上表开放直接关系路径。

### 4.3 组织下级与跨组织协作

- 组织授权默认精确匹配。`includeDescendants=true` 必须随授权事实单独保存；组织闭包从 IAM 同步数据构建并校验环路、孤儿和版本。
- 跨组织支持通过显式服务、队列、CI 范围或受控工单参与关系实现，不能依靠“支持人员”或“平台管理员”宽角色。
- 关联工单两端分别授权；能够读取源单不表示能够读取目标单。无权目标不返回标题、状态、组织、是否存在或关系数量。

## 5. 团队与团队队列

### 5.1 对象模型

| 对象 | 作用 | 核心约束 |
| --- | --- | --- |
| 支持团队 | 运维责任组织 | 稳定团队编码、生命周期、责任组织和负责人 |
| 团队成员 | 用户在团队中的活动成员关系 | 绑定 IAM ID、成员角色、有效期和版本 |
| 团队队列 | 可路由和可抢单的工作池 | 稳定队列编码、所属团队、生命周期和路由模式 |
| 队列覆盖范围 | 队列可处理的组织/系统/目录/CI 范围 | 服务端发布，范围变化版本化 |
| 任务队列快照 | 待办创建时的队列和策略事实 | 固化队列、策略版本、候选范围和时间 |

个人视图不是可配置队列：`MY_TODO`、`MY_DONE`、`MY_REQUESTED`、`TO_READ` 等只根据当前主体和已授权对象派生。团队队列必须通过稳定 `queueCode` 查询，浏览器传入队列编码只能选择当前上下文已授权的队列。

### 5.2 入队、可见与抢单

1. 流程进入处理节点时，服务端按已发布的系统/目录/节点路由策略解析团队队列。
2. 创建任务时固化队列编码、策略版本和候选范围；没有合格队列时进入受控未分派状态并告警，不能落入全局默认池。
3. 团队待办 SQL 同时验证活动任务、活动队列、活动成员、主体数据范围和流程状态。
4. 抢单以任务未领取、预期任务版本、预期工单/流程版本、当前主体仍有资格为同一原子条件；数据库成功后才推进 Flowable 和业务投影。
5. 并发失败返回冲突并重新读取，不重试为另一个人的成功结果。

团队离队、IAM 停用或撤权立即移除未领取任务可见性。已领取任务不静默转交；系统产生风险告警，由队列主管执行受审计的回收、转派或交接。

### 5.3 物理模型与范围语义

`support_team` 以 `team_code` 为稳定主键，包含名称、所属 IAM 组织、负责人 IAM ID、生命周期、乐观版本及创建/更新审计字段。`support_team_member` 以团队和 IAM 用户为业务键，保存 `MEMBER` 或 `SUPERVISOR`、`effective_from`、`effective_until`、活动状态和版本；禁止同一用户在同一团队存在时间重叠的多条活动事实。

`support_queue` 以 `queue_code` 为稳定主键并外键关联团队，保存名称、分派模式、生命周期和版本。`support_queue_scope` 以队列、范围类型和范围 ID 为业务键，首批只允许 `ORGANIZATION`、`SERVICE_CATALOG`、`SERVICE_SYSTEM`、`CONFIGURATION_ITEM`。同一队列同类型多个值取并集，不同类型取交集；一个队列的覆盖范围与人员的 `TicketAccessScope` 必须同时命中目标工单，任何一方都不能替代另一方。

`SUPERVISOR` 是队列治理成员角色，只允许在该团队的活动队列内执行候选查询、分派、回收、停用处置和风险查看；它不隐含全组织、全服务或全集团工单读取。

### 5.4 任务事实和不可变路由快照

`ticket_workflow_task.queue_code` 保存当前任务所属工作池。每次队列路由同时向 `ticket_workflow_queue_routing_snapshot`（最终名称可在 V40 评审中冻结）追加一条不可变记录，至少包含：快照 ID、工单 ID、工作流任务 ID、节点、团队/队列编码、分派模式、目录节点策略版本、队列版本、队列范围摘要、候选角色、具体候选成员集合、目标 `TicketObjectContext` 摘要及捕获时间。

快照一经创建不可更新或覆盖。同一工单再次进入同一节点时必须生成新的任务和快照；任务当前状态、领取人和版本保存在任务投影，领取/取消/完成另记事件，不能通过改快照表达当前状态。

### 5.5 共享领取原子条件

共享领取只有在以下事实同时成立时才能成功：

```text
任务状态 = OPEN 且未领取
AND queue_code、任务版本、工单版本、流程版本均符合预期
AND 队列为活动状态
AND 当前时间处于成员有效期且成员状态活动
AND IAM 用户、后台授权和所需支持角色均活动
AND 人员 TicketAccessScope 命中目标 TicketObjectContext
AND support_queue_scope 命中同一目标 TicketObjectContext
AND 当前 Flowable 引擎任务仍可领取
```

数据库 CAS、Flowable 领取、主办投影、任务版本、不可变事件、SLA 和通知必须处于同一可回滚业务事务；只允许一个成功者。失败方返回冲突并重新读取，不把重复请求解释成自己的成功，也不在失败事务外发送通知。

### 5.6 停用、离队和责任处置

- 队列停用立即阻止新路由和新领取。未领取任务进入受控治理清单，只有对源、目标队列均有治理资格且范围命中的主管可迁移；不能自动进入全局默认队列。
- 成员离队、成员过期、IAM 停用、后台停用或角色/范围撤销后，下一请求立即失去队列目录、未领取列表、候选展示和领取能力。
- 已领取任务保留原主办与路由快照，不静默转移；系统生成责任风险，由有效主管走回收、转派或交接。原处理人后续动作仍须通过当前角色和范围门禁。

### 5.7 生命周期审批与受控跳转候选

候选资格采用三阶段重算：

1. **创建申请：** 读取目标工单当前 `TicketObjectContext`；从策略候选角色获得活动 IAM/后台用户，逐人解析当前 `TicketAccessScope`，只保留范围命中、职责分离通过且不是申请人的具体 IAM ID，并固化候选集合、范围摘要和策略/流程版本。
2. **展示待办：** 只从当前 Flowable 活动任务出发，且当前主体必须仍在冻结集合、角色仍有效、当前范围仍命中目标工单。失权任务不展示、不计数，后续扩大角色或范围也不把新人员加入旧申请。
3. **提交决定：** 再次读取目标 `TicketObjectContext`、活动引擎任务和候选人的当前 `TicketAccessScope`。冻结身份、浏览器中的 `canDecide` 或曾经可见均不能替代当前门禁；失败只记录稳定拒绝原因，不追加有效决定、不改变申请状态、不执行工单动作。

受控跳转和生命周期审批必须采用同一候选过滤端口与契约测试，不能各自解释范围。候选冻结后失权的任务如何取消、替补或重新发起属于独立受审计流程；首批实现不得自动把任务转给同角色其他人员。

### 5.8 队列命令幂等模型

`support_queue_command_idempotency` 使用 `(actor_iam_user_id, idempotency_key)` 主键，核心字段包括：`operation`、`resource_type`、`resource_code`、`request_fingerprint`、`status`、`response_status`、`response_summary`、`error_code`、`created_at`、`completed_at`、`expires_at` 和版本。`status` 至少区分 `IN_PROGRESS`、`SUCCEEDED`、`FAILED_RETRYABLE`、`FAILED_FINAL`。

请求指纹由服务端对规范化命令计算，必须覆盖操作、资源、版本、原因、替代队列、有效时间和所有业务字段，不含 CSRF、Cookie 或链路 ID。响应摘要仅保存重放所需的资源版本、计划 ID、结果计数和安全错误码，不保存完整成员资料或异常堆栈。

原子插入成功者获得命令执行权；主键冲突时比较所有绑定字段。同绑定的最终结果稳定重放，处理中不重复执行，不同绑定一律冲突。TTL 后由受控任务清理；高风险业务事实仍由迁移计划、快照、事件和审计长期保存。

### 5.9 队列迁移计划状态机

`support_queue_migration_plan` 保存计划 ID、源/目标队列、两端版本与范围摘要、申请/批准/执行主体、预演统计、计划状态、执行租约、结果摘要及各阶段时间。`support_queue_migration_plan_item` 逐任务保存任务/工单/流程版本、预演领取状态与主办、源/目标队列、原路由快照、处置类型、交接清单摘要和结果。

计划和明细的预演字段不可修改；计划状态、租约和结果以乐观锁/CAS 更新。状态转换仅允许：

```text
PREFLIGHTED → APPROVED → EXECUTING → COMPLETED
                                    ↘ FAILED
PREFLIGHTED / APPROVED → STALE | CANCELLED
```

批准时重新验证申请人不能自批、批准人的当前角色/两端范围、计划未过期和两端队列版本。执行时再验证相同事实并原子认领租约；批准本身不能迁移任何任务。

### 5.10 逐任务迁移与交接

- 目标队列范围按每个范围类型构造集合，只有目标集合逐项包含源集合才是超集；不能把“目标命中当前工单”误当作覆盖整个源队列。
- 未领取项保存预演时任务版本、`OPEN`、无领取人、源 `queue_code`、工单/流程版本。执行使用全部字段 CAS；成功后写目标队列、递增版本、追加迁移结果、路由快照和审计。
- 在办项保存主办和领取状态，执行不改变任务或主办，只追加 handover checklist。清单包含未完事项、SLA、目标主管、截止时间和原始路由证据，后续交接仍走独立 Flowable/业务流程。
- `BLOCKED` 项、失败 CAS、缺失清单或范围/版本变化阻止计划完成。部分成功项保持成功且幂等，剩余项按结果重试或重新预演，不能整批盲目重放。

### 5.11 重试、租约与并发

同一源队列的活动计划使用唯一条件限制为一条。执行器以 `(plan_id, APPROVED, version)` 切换到 `EXECUTING` 并写有期限租约；仅租约所有者可写结果，租约到期后新执行器先读取明细结果再恢复。

任务领取与迁移竞争同一任务版本和领取状态：仅一个 CAS 成功。重复迁移、重复批准、重复完成和重试成功项均返回已有事实，不重复创建快照、清单、通知或审计。进程在数据库提交后响应前崩溃时，客户端以原幂等键得到已提交结果。

### 5.12 V43 幂等执行租约

`support_queue_command_idempotency` 在 V43 增加：

| 字段 | 作用 | 约束 |
| --- | --- | --- |
| `lease_owner` | 当前执行实例/命令执行 ID | 服务端生成；浏览器不可提交；终态后可保留用于追溯 |
| `lease_expires_at` | 当前执行权到期时间 | 使用数据库 UTC；未过期不能接管 |
| `attempt_count` | 成功 reserve/接管次数 | 仅 CAS 成功后递增；客户端重试次数不等于该值 |
| `key_version` | HMAC 密钥非敏感版本 | 用于选择受管验证密钥；不能回显密钥内容 |
| `result_resource_type/id` | 已提交业务结果引用 | 只保存稳定类型和 ID；用于崩溃后对账和响应重建 |

首次 reserve 是唯一键插入；过期接管使用主体、键、`IN_PROGRESS`、旧租约所有者、过期时间和记录版本的 CAS。数据库服务器时间是租约判断依据，应用节点本地时钟不能提前获得执行权。

### 5.13 结果优先的恢复算法

同键同绑定遇到 `IN_PROGRESS` 时按以下固定顺序处理：

```text
租约仍有效 → 返回处理中冲突 / Retry-After
租约已过期 → 按 result_resource_type/id 与操作自然键查询业务结果
业务结果已存在且绑定一致 → 不执行命令，只补全幂等 SUCCEEDED 和响应摘要
业务结果不存在 → CAS 接管租约，重新校验当前授权/版本后执行
结果存在但绑定不一致或不可证明 → FAILED_FINAL + 人工治理
```

每类操作必须声明可验证的结果：创建队列用稳定队列编码，更新/激活/停用用队列编码与结果版本，预演/批准/执行/重试/取消用计划 ID、计划版本及逐项结果。禁止仅凭日志、异常缺失或客户端超时推断业务未提交。

### 5.14 事务边界

同一 MySQL 内的队列/计划/明细写入、结果资源引用和幂等完成尽量在同一事务提交。Reserve 可在业务事务前独立提交以阻止并发；业务事务成功时必须同时写稳定结果引用和幂等终态。

若 Flowable/外部步骤不能与数据库原子提交，先在业务库保存可恢复意图和命令关联；恢复器只推进未完成步骤。业务结果已存在时不得再次调用创建、迁移、通知或审批写入。幂等表是执行协调证据，不替代业务表的唯一键、版本 CAS、不可变事件和 Outbox。

### 5.15 HMAC 规范化与密钥版本

- 指纹算法固定为 HMAC-SHA256。规范化输入采用版本化格式，固定 Unicode NFC、字符串空白规则、UTC 时间、十进制数字、对象键排序、集合排序、空/缺失字段区别及枚举大小写。
- 受管密钥至少 32 字节，并按环境隔离。`key_version` 是部署登记的稳定非敏感 ID；同一环境同一时刻只有一个写入版本。
- 校验采用记录版本精确选键，轮换窗口允许当前/上一版本读取；新记录只写当前版本。未知版本关闭式失败并告警，不能遍历全部密钥试验。
- 旧密钥退役前检查其记录的最大 TTL、活动租约、失败恢复和归档状态。密钥轮换不修改历史指纹、不重置幂等键，也不改变请求规范化版本。

### 5.16 V44 历史记录分类

V44 对旧幂等记录执行关闭式分类：

| 历史事实 | V44 状态 | 允许能力 |
| --- | --- | --- |
| `SUCCEEDED` 且强结果引用可验证 | `LEGACY_RESULT_ONLY` | 当前授权下查询最小状态/资源引用；禁止 payload 重放和执行 |
| `SUCCEEDED` 但无强结果引用 | `RECONCILIATION_REQUIRED` | 仅人工对账；禁止自动成功、接管或重做 |
| 任意 `IN_PROGRESS` | `RECONCILIATION_REQUIRED` | 清除执行资格；不依据旧租约接管 |
| 任意历史失败 | `FAILED_FINAL` | 只读状态/审计；禁止 retry |

所有上述历史记录的 `key_version` 写为 `LEGACY_UNVERIFIABLE`。该值只是治理分类，不是密钥版本，不能出现在 HMAC key ring，也不能用于计算/验证指纹。

### 5.17 Legacy 查询与治理边界

- 状态查询先按当前主体和资源数据范围授权，再返回操作、资源、legacy 状态、结果资源类型/ID和安全原因码；不返回历史请求、响应 payload、成员/范围内容或旧指纹。
- `LEGACY_RESULT_ONLY` 的强引用必须在迁移时验证目标资源存在、类型匹配且属于原主体/操作边界；后续资源变化不把记录升级成可重放命令。
- `RECONCILIATION_REQUIRED` 的人工处置只能追加“已确认结果引用”或“最终失败”治理事件。处置不修改原请求指纹、主体、幂等键、操作和资源绑定，不生成租约。
- Legacy 记录不参与当前/上一 HMAC 双读；服务端看到 `LEGACY_UNVERIFIABLE` 时直接进入 legacy 分支，禁止尝试所有密钥或将 HMAC 失败解释为新命令。

## 6. SQL 层数据范围

### 6.1 强制查询顺序

所有工单集合查询遵循同一逻辑顺序：

```text
可信授权上下文
→ SQL 授权谓词
→ 业务筛选谓词
→ 稳定排序
→ LIMIT / 键集游标
→ 最小字段映射
```

禁止以下实现：

- `SELECT` 全部候选工单后在 Java Stream 中调用 `canRead` 再分页；
- 先查全局 `COUNT(*)`、队列数量或聚合，再隐藏无权明细；
- 从搜索、缓存或报表取得全局 ID 集合后逐条鉴权；
- 将组织路径、角色、排序列或范围列表拼接成 SQL；
- 以平台角色、HTTP 路由保护或前端菜单替代对象范围谓词。

### 6.2 范围谓词来源

范围谓词只能来自服务端解析的有界参数、授权包关系表、组织闭包、团队成员/队列关系和直接对象关系。SQL 必须保持“包内不同类型交集、包间并集”的括号结构，不能把各类型值分别展开后产生笛卡尔扩权。大范围授权不得生成超长 `IN (...)`；应使用参数化 `EXISTS`、连接受控范围表、数据库会话临时范围或经过评审的等价方式。

详情接口在按主键读取后仍执行对象和动作授权。集合查询与详情授权必须复用同一判定语义并通过契约测试防止漂移。

## 7. 分页、排序与数量

### 7.1 不透明游标

- 默认顺序固定为 `created_at DESC, id DESC`，仅使用不可变创建时间和唯一工单号，保证相同数据集下顺序确定。
- 首次查询记录 `asOf` 上界；后续页仅查询 `created_at <= asOf`，避免新建工单插入前页造成重复。
- 游标至少绑定主体、范围版本、规范化筛选哈希、排序、`asOf`、上一页末尾 `(created_at,id)` 和过期时间，并由服务端签名或加密；客户端不得解析或修改。
- 当前主体、范围版本、筛选或排序不一致时拒绝旧游标并要求重新从第一页读取。游标不延长登录会话，也不保存当时已经撤销的权限。
- 默认页大小 20，最大 100。负数、零、超限、未知筛选或未知排序安全拒绝。

首批 P0 不开放按任意字段排序。SLA 风险、更新时间、优先级等可变排序需在后续为独立工作台查询定义稳定快照语义和专用索引，不能复用默认游标后临时添加。

### 7.2 数量与空页

列表默认可只返回 `items`、`pageSize` 和 `nextCursor`。若兼容契约仍要求 `total`，必须用与列表完全相同的授权和业务谓词计算，并单独满足容量指标。仪表盘角标使用当前主体的专用范围查询或按范围隔离的受控汇总，不允许读取全局数量后扣减。

无权数据不得改变对外可观察的总数、页数、空页、错误详情或聚合。对象详情的不存在和无权响应遵循统一防枚举契约。

## 8. 数据库迁移与索引

### 8.1 迁移策略

第一批范围查询索引由 V39 承载；团队队列结构使用 V40，不修改 V1–V39。V40 按以下顺序实施：

1. 新增团队/队列/成员/覆盖范围、可空任务 `queue_code`、不可变任务队列快照及必要索引。
2. 以有界批次回填历史工单、任务和范围关系，记录批次、水位、行数、失败原因和校验摘要。
3. 应用进入兼容阶段：旧数据可读，新写入同时固化完整范围；比较旧、新授权查询结果并只记录脱敏差异。
4. 校验无空范围、无孤儿、无重复活动成员/队列和无越界映射后切换 SQL 查询。
5. 最后收紧非空、唯一键和外键；回退应用时保留新增结构与审计数据，不执行破坏性降级。

回填不得在高峰期持有大事务或长时间元数据锁。批次必须可暂停、可续跑且幂等；失败时停止切流，不伪造 Flyway 成功。

### 8.2 最小索引族

最终列名以迁移评审为准，但至少需要覆盖：

- 工单默认稳定分页：`(created_at DESC, id DESC)`；
- 提单人个人视图：`(requester_iam_user_id, created_at DESC, id DESC)`；
- 组织和服务目录范围：范围键加 `(created_at DESC, id DESC)`；
- 活动团队队列任务：`(queue_code, status, created_at, id)`；
- 当前处理人待办/已办：处理人、任务状态和稳定时间键；
- SLA 风险：风险/截止时间与工单 ID；
- 授权与成员反查：主体、活动状态、范围类型/ID、有效期和版本。

索引是否保留由生产等价数据的 `EXPLAIN ANALYZE`、锁等待、写放大、存储增长和查询频率共同决定。重复或低选择性索引不得仅因测试数据通过而进入生产。

### 8.3 V40 团队队列迁移设计

V40 是 V39 之后的前向扩展，包含：`support_team`、`support_team_member`、`support_queue`、`support_queue_scope`、不可变队列路由快照表，为节点分派策略和 `ticket_workflow_task` 增加可空 `queue_code`，以及成员有效期、活动队列、范围反查和队列任务所需索引。

迁移按以下阶段发布：

1. **扩展：** 创建新表、可空列和索引；旧应用继续运行，新应用尚不从团队队列读取。
2. **双写：** 新建任务同时写旧分派快照和新队列快照；写入失败整体回滚，不能只保留其中一份。
3. **回填：** 仅对能从已发布目录 × 节点策略证明唯一队列的历史活动任务分批回填；零匹配、多匹配或历史版本缺失进入人工治理清单。
4. **校验切读：** 比较任务、队列、范围、候选集合和快照摘要，确认无孤儿、无非法成员区间、无错误默认队列后切换团队查询和领取。
5. **收紧：** 仅对确定要求队列的任务类型收紧 `queue_code` 非空和引用约束；兼容旧类型继续显式为空并 fail-closed。

回退旧应用保留 V40 表、列和所有快照；修复只能新增前向迁移。回填任务必须幂等、可暂停、可续跑并保留水位、行数和原因摘要，禁止修改 V1–V39 或删除已写路由证据。

### 8.4 V42 幂等与迁移计划设计

V41 已用于知识组织/目录范围，队列命令幂等和迁移计划使用 V42。V42 新增 `support_queue_command_idempotency`、`support_queue_migration_plan`、`support_queue_migration_plan_item` 及必要结果/交接字段、唯一约束和索引；不修改 V1–V41。

最小唯一与索引要求包括：主体+幂等键主键、操作/资源指纹校验、同源队列活动计划唯一门禁、计划状态/租约到期扫描、计划明细 `(plan_id, disposition, result_status, task_id)`、任务版本 CAS、handover checklist 待办和 TTL 清理索引。具体索引需用真实数据 `EXPLAIN ANALYZE` 决定，不能用 JSON 全表扫描替代结构化键。

数据库验证矩阵：

1. 全新 MySQL 空库顺序执行 V1–V42 并完成应用启动冒烟。
2. 导入当前结构基线、登记正确 Flyway 版本后执行后续迁移至 V42。
3. 从保留 Flyway 历史的旧环境逐版本升级，校验所有历史 checksum 未变。
4. 从含大规模 V40 团队、队列、任务和路由快照的副本升级，核对行数、外键、范围与快照摘要。
5. 发布失败时回退旧应用并保留 V42 表/数据；停止新执行租约，按前向修复和租约恢复继续，不执行破坏性 down migration。

### 8.5 V43 租约、结果引用与密钥版本

V43 只为 V42 幂等表增加租约、尝试次数、密钥版本和结果资源引用及相关索引。现有终态记录按可证明的安全摘要回填资源类型/ID；现有 `IN_PROGRESS` 记录发布前必须先对账，不能统一清空或直接视为可接管。

关键索引至少覆盖：`(status, lease_expires_at, version)` 过期扫描、`(result_resource_type, result_resource_id)` 结果对账、`(key_version, status, expires_at)` 密钥退役与清理，以及既有主体+幂等键点查。接管更新必须使用全部预期条件，不能先查后无条件更新。

发布顺序为：扩展可空列/索引 → 部署双读旧/新记录的代码 → 对账回填终态结果引用 → 启用 HMAC 新写和租约接管 → 验证旧记录/旧密钥 → 按制度退役。回退保留全部 V43 数据，先关闭新接管和写入口，再由旧应用只读兼容或前向修复。

### 8.6 V44 历史幂等治理

V44 扩展命令状态约束，完成 legacy 分类并将 `key_version` 收紧为非空。迁移前必须停止队列写入/接管，避免分类过程中产生新的 V43 记录；迁移后先运行一致性自检，再开放新写。

迁移 SQL 必须使用可审计、确定性的条件更新，分别统计：有强引用成功、无引用成功、进行中、失败、NULL/未知版本和异常资源绑定。批次结果写入部署证据，不得用一个无条件 UPDATE 抹平来源状态。

最小数据库门禁：

- `key_version IS NULL = 0`；
- `LEGACY_UNVERIFIABLE` 只对应 `LEGACY_RESULT_ONLY/RECONCILIATION_REQUIRED/FAILED_FINAL`；
- legacy/治理状态的 `lease_owner/lease_expires_at` 不具有活动执行意义；
- 活动 reserve/接管查询明确排除 legacy 与治理状态；
- payload 重放查询仅允许可验证 HMAC 的 `SUCCEEDED`，并排除 `LEGACY_RESULT_ONLY`。

真实 MySQL 验证 V1–V44 空库、V42/V43 历史副本升级和旧应用回退。回退保留 V44 状态与非空约束；旧应用不理解新状态时只能保持写入口关闭，不能通过状态降级恢复运行。

## 9. 安全验收矩阵

至少构造两个组织、两个服务系统、两个服务目录、两个团队队列、共享 CI、跨组织协作和同名工单数据，覆盖：

- 提单人、主办、协办、代理、审批人、一线、二线、服务经理、审计员、平台管理员；
- 精确组织、包含下级、服务、队列、CI、显式全局范围和无范围；
- 详情、列表、搜索、数量、个人队列、团队队列、关联、评论、附件、审批、报表和导出；
- IAM 停用、调岗、后台撤权、团队离队、队列停用、范围版本变化和旧游标重放；
- 客户端篡改组织、系统、目录、队列、排序、游标、页大小和目标对象 ID；
- 共享队列至少 50 个并发抢单请求，断言唯一成功者及单一流程推进/通知事实。
- 生命周期审批与受控跳转分别验证创建、展示、决策三阶段：跨范围候选排除、申请人排除、冻结后扩权不新增候选、冻结后撤权/调岗不可见且不可决定。
- 队列停用、成员离队/过期、IAM/后台停用和范围撤销后立即收敛；历史快照保持不变，未领取和已领取任务进入规定的治理路径。
- 幂等键覆盖同绑定重放、不同绑定冲突、处理中并发、可重试/最终失败、TTL 清理和响应前崩溃；任何场景均不得重复业务事实。
- 迁移计划覆盖范围超集、职责分离、状态越级、租约竞争、任务状态漂移、未领取迁移 CAS、在办清单和部分失败恢复。
- V43 覆盖活动租约冲突、过期前结果对账、唯一 CAS 接管、业务提交后补终态、错误结果绑定和旧执行者越权写入。
- HMAC 覆盖规范化等价/差异向量、未知密钥版本、当前/上一版本双读单写、轮换中断和旧密钥安全退役。
- V44 覆盖四类历史事实分类、NULL 版本收紧、legacy 状态查询、旧键/payload 重放拒绝、人工对账审计和启动自检失败关闭。

任何拒绝路径都不得返回无权对象标题、组织、人员、状态、附件、关系、候选人、总数或存在性差异。测试必须在真实 MySQL 与实际 Spring Security/Flowable 组合上执行，内存仓库仅作快速单元反馈。

- V40 扩展、双写、唯一映射回填、异常治理清单、切读、旧应用兼容和前向修复演练；
- 审批候选创建/展示/决策三阶段的冻结集合、当前范围、拒绝原因和无越权决定证据；
- V42 幂等自然键、活动计划唯一性、逐项任务快照、执行租约、未领取 CAS、在办交接清单、TTL 清理和稳定重放证据；
- 真实 MySQL V1–V42 空库、历史基线升级、V40 存量升级、关键 SQL `EXPLAIN ANALYZE` 和旧应用回退证据；
- V43 租约字段回填、结果资源对账、业务/幂等事务故障注入、接管 CAS、HMAC 密钥轮换、真实 MySQL V1–V43 与应用回退证据；
- V44 历史分类前后数量、强引用验证、`key_version NOT NULL`、legacy 查询隔离、治理审计、真实 MySQL V1–V44 与旧应用关闭式回退证据；
- DBA、安全、IAM、服务台和运维负责人签字。

任一证据缺失、范围查询仍依赖应用层全表过滤、宽角色仍可绕过业务范围、真实 MySQL 未通过或容量目标未达到时，发布结论必须为“不具备集团生产上线条件”。

## 11. 前端只读能力与草稿的数据权限边界

### 11.1 Capabilities 与授权上下文

- capabilities 由当前可信 IAM 主体和服务端授权解析器生成，使用稳定能力码和授权摘要版本；不得把完整组织/服务/CI 范围集合、候选人集合或内部角色绑定下发为前端授权规则。
- 平台入口能力不等于业务数据范围，对象 capability 不等于长期授权。所有集合查询、Dashboard 下钻和对象动作继续执行本文定义的当前 `TicketAccessScope` 与 `TicketObjectContext` 门禁。
- 客户端能力缓存、历史响应和离线草稿均不能恢复已撤销权限；授权摘要变化时游标、Dashboard 快照和需要范围绑定的草稿操作失效并重新解析。

### 11.2 Dashboard 查询约束

- Dashboard 指标是受控查询目录中的只读查询，每项显式声明适用角色、范围谓词、聚合维度、时间窗口、最大成本和下钻筛选。动态 SQL、任意维度和浏览器提交范围表达式不在首批范围。
- 响应包含 `scopeDigest`、`asOf`、口径版本和逐指标 availability。数量与下钻列表共用同一授权谓词；无法满足同一快照时必须暴露数据时点差异，不能宣称强一致。
- 缓存键必须包含授权摘要和查询口径，缓存内容按范围隔离；撤权优先于缓存命中。无权、不可用和真实零值采用不同稳定状态，但错误差异不得泄露其他组织对象是否存在。

### 11.3 草稿与表单版本范围

- 服务端草稿至少绑定主体 IAM ID、请求人组织、目录/系统、`formSchemaId@version`、版本、TTL 和创建时范围摘要。读取/更新/提交使用当前权限；创建时摘要只用于检测漂移，不保留历史访问权。
- 浏览器只能持久化批准的低敏字段和无权能引用，禁止附件内容/下载地址、token、Cookie、CSRF、幂等键、内部评论、人员目录、敏感字段和授权范围。临时附件始终独立鉴权且非清洁状态不可下载。
- schema 和步骤元数据不能扩大字段读写权限。隐藏、只读、服务端派生和敏感字段由服务端字段策略控制；客户端提交额外字段、旧版本字段或跨目录 schema ID 均拒绝并审计安全摘要。

### 11.4 版本映射和兼容门禁

- 目录发布包引用的 schema、流程定义、路由和 SLA 版本在建单时固化，后续发布不改变历史 `TicketObjectContext`、审批候选、队列范围或流程实例。发布包选择本身需要目录治理权限，不能替代业务对象范围。
- 旧前端未知新 capability、availability、schema 步骤或发布包字段时必须安全忽略并隐藏新入口；服务端在兼容期继续执行完整授权和字段校验，不能因旧客户端缺字段而使用宽默认值。
- 验收覆盖跨组织同名指标、能力缓存篡改、Dashboard 缓存污染、草稿跨主体/跨组织读取、schema/目录版本替换、撤权后提交、旧游标下钻及发布包版本漂移。任何场景不得泄露数量、字段、附件、候选人或历史范围。
