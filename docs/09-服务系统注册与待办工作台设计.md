# 服务系统注册与待办工作台设计

## 1. 目的与边界

“影响系统”从全局字典升级为服务系统注册中心。它维护工单平台用于表单联动、目录选择、路由和运营统计的支持元数据；不写入、不替代 CMDB 的 CI 主数据。每个系统可只读关联一个受管 CI，CI 的生命周期、属性和发现结果仍由 CMDB 管理。

本设计覆盖系统、系统模块、服务目录映射、路由衔接、工单历史快照和待办工作台布局。浏览器不能提交系统负责人、组织、候选角色、路由策略、CI 归属或历史快照。

## 2. 数据模型

| 对象 | 作用 | 核心约束 |
| --- | --- | --- |
| `service_system_registry` | 已注册的服务系统 | 系统编码稳定；状态为草稿、已发布或已退役；可只读关联 CI |
| `service_system_module` | 系统下的可选受影响模块/页面 | 模块编码仅在本系统内唯一；退役模块不可用于新单 |
| `service_system_catalog_mapping` | 系统可使用的服务目录 | 目录必须已存在；支持默认目录 |
| `service_system_module_catalog_mapping` | 模块级目录收敛 | 优先于系统级默认映射；不能映射任意客户端目录 |
| `ticket_service_system_snapshot` | 提单时的系统/模块/目录证据 | 不随系统改名、模块调整或目录变动被改写 |

所有变更使用版本号、更新人、时间和变更说明；后续后台页面采用草稿、复核、发布、停用、回滚治理，不能由普通提单页面编辑。

当前实现已提供后台系统注册、模块维护、系统级/模块级目录映射和发布/退役入口；V38 以追加式生命周期事件保存创建、更新、发布与退役的审计证据。后台操作按服务经理/平台管理员及组织数据范围校验，前台仅返回当前 IAM 组织下的已发布系统。

## 3. 提单联动

```mermaid
flowchart LR
  A[选择影响系统] --> B[仅加载该系统已发布模块]
  B --> C[模块映射服务目录]
  C --> D[目录映射节点路由策略]
  D --> E[创建工单并固化系统/模块/目录快照]
```

影响系统为空时，只有目录明确允许“非系统类事件”的服务才可提交。系统已选择时，前端只展示服务端返回的模块和允许目录；提交时服务端重新校验系统状态、模块归属、目录映射、对象权限和版本，不能相信浏览器回传的关联关系。

## 4. 待办工作台

待办处理页面采用两栏工作区：左侧为工单处理表单（事实、影响系统/模块快照、处理结论、附件、流程动作）；右侧为固定协作区（当前主办/协办、添加协办、内部评论、交接/转办、流程与 SLA 摘要）。右侧协作区只显示服务端按工单对象权限、主协办关系与当前流程返回的能力。

当前前端已实现系统→模块→目录收敛和详情页左处理/右协作布局。注册中心不可用或当前组织没有已发布系统时，提单页面明确提示并禁用系统关联的提交路径，不用演示字典或浏览器默认值绕过服务器映射校验。

抢单仅发生在目录节点配置为共享待办时。抢单是原子主办占有：同一版本仅一人成功，失败方重新读取当前主办；不接受客户端指定主办人。系统随机分派、共享待办抢单和上一节点指定都必须记录节点策略版本、候选角色池和实际处理人快照。

### 4.1 队列目录与角色语义

待办工作台分为个人视角和团队视角。个人视角沿用我的待办、逾期待办、今日完成、我已办、我发起的、草稿箱、我的待阅和所有可见工单；团队视角至少提供团队未领取、团队处理中、团队临近违约、团队已违约和待交接。团队视角不是“所有可见工单”的快捷筛选，而是服务端依据当前用户的队列成员、管理职责、服务范围、CI 范围和值班有效期计算出的责任集合。

| 角色 | 默认队列能力 | 明确限制 |
| --- | --- | --- |
| 提单人 | 个人发起、草稿、待阅和被授权可见工单 | 无团队队列、候选人和处理组枚举权 |
| 一线/二线支持 | 个人待办；获授权团队的未领取、处理中和 SLA 风险视角 | 只能领取活动角色池内且当前可处理的任务 |
| 主办/协办 | 个人任务及其所属授权团队视角 | 对单张工单的协作权限不推导来源组织队列权限 |
| 队列主管/服务经理 | 明确管理队列的数量、列表、分派、回收和升级能力 | 不得越出管理队列、服务、CI 或数据密级范围 |
| 审计员 | 获授权范围的只读队列、详情和审计事件 | 没有抢单、转派、评论或状态动作 |
| 平台管理员 | 队列与路由配置；另行授权的数据范围内可排障读取 | 配置管理角色不自动拥有集团业务数据全量读取权 |

工作台初始化时，服务端返回当前主体可选择的队列目录，其中包含稳定队列编码、展示名称、队列类别、数据范围摘要、允许筛选/排序字段和可用动作。客户端只能回传该目录中的编码；服务端每次查询仍重新解析权限，目录缓存不能作为授权凭据。

### 4.2 集团数据隔离与跨组织协作

工单数据范围由组织、服务系统/目录、团队队列、CI 和对象密级共同决定。列表 SQL、数量 SQL、详情、候选人、通知和导出必须复用同一授权谓词；后台人员的配置权限与工单业务数据读取权限分离。组织范围采用 IAM 稳定 ID 与受控组织树版本，不能由客户端提交组织名称或父子路径。

跨组织协作采用“单对象、限动作、限时效”授权：

- 发起协办、交接或转派前，来源主体必须对工单具有相应动作权限；目标必须属于服务端返回的活动队列/角色候选集合。
- 确认或审批通过前不授予目标主体工单处理权；通过后仅授予完成该工单任务所需的正文、附件、内部评论和动作能力，不开放来源组织的队列列表、汇总数量或人员目录。
- 协办完成、交接/转派失效、人员停用、对象关闭或授权撤销时，临时权限按策略回收；历史协作身份和审计事件不被删除。
- 数据密级高于目标主体上限时，即使角色、队列和组织条件命中也必须拒绝；错误响应不能泄露工单标题、来源组织、附件或候选人数。

### 4.3 数据库稳定分页

核心工单和团队队列使用数据库游标分页，不使用“固定查询第一页 + 浏览器当前页过滤”。查询顺序固定为：解析当前 IAM 授权范围 → 构造队列责任谓词 → 应用业务筛选 → 应用白名单排序及稳定编号决胜键 → 应用游标边界与页大小。

- 默认页大小为 20，可选 20、50、100，服务端拒绝更大值。第一批默认排序为 `created_at DESC, ticket_id DESC`，只使用不可变键形成稳定快照；其他排序必须另行定义快照语义并列入服务端白名单，且始终追加 `ticket_id` 决胜。
- 游标为不透明、可校验值，绑定 IAM 主体、授权版本、队列编码、筛选摘要、排序、最后一条排序值和查询快照；不能由浏览器解码、修改或跨查询复用。
- 关键词、状态、类型、优先级、服务目录、影响系统、申请组织、SLA 风险和日期范围均在数据库分页前过滤。组织、人员、服务和队列标识只接受服务端授权目录返回的稳定 ID。
- 同一快照逐页遍历时，未变化记录不重复、不漏项；新增或更新记录在主动刷新后的新快照展示。授权撤销实时优先，旧游标后续页也不得继续返回已失权对象。
- 需要总数的视图使用与列表相同的授权/筛选谓词和快照；无权或不应披露总量的队列不返回总数。不得以不同错误、空页数量或查询耗时泄露其他组织数据。
- MySQL 验收必须证明分页边界和授权条件在 SQL 中执行，并覆盖常用复合索引；禁止查询全量工单、在 Java 内存中过滤后截取页面，也禁止前端自行计算跨页总数。

### 4.4 团队、成员与队列持久化模型

| 表 | 关键字段 | 约束 |
| --- | --- | --- |
| `support_team` | `team_code`、名称、所属组织、负责人、状态、版本 | 团队编码不可复用；负责人是治理联系人，不自动获得业务数据权限 |
| `support_team_member` | 团队、IAM 用户、`MEMBER/SUPERVISOR`、生效/失效时间、状态、版本 | 同一时刻仅一条有效成员事实；用户、后台角色和成员均须活动 |
| `support_queue` | `queue_code`、团队、名称、分派模式、状态、版本 | 队列编码不可复用；仅活动队列可接收或领取新任务 |
| `support_queue_scope` | 队列、范围类型、范围 ID、状态、版本 | 支持组织、服务目录、服务系统、CI；同类型并集、不同类型交集 |

成员关系是队列资格，不是独立工单授权。普通成员和主管均须以当前 `TicketAccessScope` 命中目标工单；主管只额外获得明确队列内的分派、回收、升级和治理动作。成员有效期按数据库 UTC 时间比较，浏览器时间、页面缓存和历史成员快照不能恢复当前资格。

### 4.5 任务队列编码与不可变路由快照

- 节点路由策略必须明确一个稳定 `queue_code`；创建队列任务时同时写入 `ticket_workflow_task.queue_code` 和独立不可变路由快照。没有唯一活动队列时任务进入 `ROUTING_REMEDIATION_REQUIRED` 等受控异常状态，不能回退到全局一线角色池。
- 快照至少保存工单、工作流任务、节点、团队/队列编码、分派模式、目录节点策略版本、队列版本、人员/队列范围摘要、候选角色和具体候选成员集合、目标工单上下文摘要及捕获时间。
- 当前任务的领取、取消、完成和转移通过任务版本与事件记录表达；不得更新历史快照伪造“当时路由到了另一个队列”。同一节点重入或重试必须生成新的任务和快照标识。

### 4.6 共享领取、停用与离队

共享领取必须在一个业务事务内完成以下原子门禁：任务仍为未领取、`queue_code` 和任务版本符合预期、工单/流程版本符合预期、队列活动、成员当前有效、IAM/后台支持角色活动、人员范围与队列范围均命中服务端目标工单上下文。成功后才写主办、调用 Flowable、追加领取事件、重算 SLA 并创建通知；任一失败整体回滚。

队列停用后立即停止新入队和新领取，未领取任务进入受控迁移清单。成员离队、过期、停用或撤权后不再出现在目录、列表和候选人中；其已领取任务进入责任风险清单，由有效主管按范围执行回收、转派或交接。系统不得自动选择任意剩余成员，也不得删除原主办和路由历史。

### 4.7 审批与受控跳转候选范围

生命周期审批和受控跳转候选不能只按角色查人。创建申请时必须用目标工单 `TicketObjectContext` 过滤候选人的当前 `TicketAccessScope`，再排除申请人并执行职责分离；冻结的是通过全部门禁的具体 IAM ID 与范围摘要。

审批工作台展示和决定写入分别再次解析当前角色、范围和目标工单上下文。旧申请冻结后新增角色或扩大范围不会获得任务；已冻结人员调岗、撤权或不再命中范围时，任务不展示且决定接口拒绝。任务处置、替补或重新发起必须走独立受审计流程，不能在浏览器中换候选人。

### 4.8 队列管理命令幂等

队列创建、更新、激活、停用以及迁移计划预演/批准/执行均使用服务端持久化幂等记录。`support_queue_command_idempotency` 以当前 IAM 主体和 `Idempotency-Key` 唯一，固化操作、资源编码、规范化请求指纹、处理状态、HTTP/业务响应状态、脱敏响应摘要和过期时间。

同键同绑定只返回第一次稳定结果；同键换主体、操作、队列或内容返回冲突。处理中命令不能由第二请求并行执行；可重试失败仍须使用原键并重新校验权限和版本。TTL 到期由后台受控清理，不允许浏览器指定、缩短或借此立即重放停用命令。

### 4.9 停用迁移计划与明细

- 停用首先生成 `support_queue_migration_plan` 和逐任务 `support_queue_migration_plan_item`，预演快照包含源/目标队列及范围版本、每个任务的 `queue_code`、状态、版本、领取人、工单/流程版本和原路由快照。
- 目标队列范围必须按组织、服务目录、服务系统、CI 逐类型覆盖源队列，且目标活动、成员/主管有效。范围少一项、类型缺失、队列或任务版本不稳定时不能批准。
- 未领取明细标记 `MIGRATE_UNCLAIMED`；在办明细标记 `RETAIN_AND_HANDOVER`；不满足条件的明细为 `BLOCKED`。预演事实不可被批准或执行步骤修改。

### 4.10 批准、执行与交接清单

迁移计划按 `PREFLIGHTED → APPROVED → EXECUTING → COMPLETED | FAILED` 推进，变化过期为 `STALE`，未执行可取消。批准人与申请人职责分离；执行器以计划版本和租约 CAS 取得执行权。

未领取任务按任务 ID、源队列、未领取状态、任务版本及工单/流程版本执行 CAS，成功后追加新路由/迁移快照。已领取任务不更新 `queue_code`、主办、流程或 SLA，只创建 handover checklist：当前主办、未完事项、风险、目标队列、主管、截止时间及原路由证据。清单缺失时队列不能宣称完成停用。

执行重试按明细结果恢复：已成功项不重做，未开始或可重试失败项重新校验，最终失败项进入人工治理。客户端超时使用原幂等键获取结果，不能用新键并行触发第二次迁移。

## 5. 前端体验支撑与流程发布映射

### 5.1 Capabilities 与工作台导航

- 工作台导航由服务端当前主体 capabilities 构造，至少区分个人工单、个人待办、团队队列、审批、知识、报表和后台治理入口。角色名称只用于服务端解析能力，不作为浏览器菜单判断条件。
- capabilities 携带授权摘要版本和生成时间；前端缓存只能用于减少闪烁，不能延长权限。能力缺失、未知或过期时隐藏入口，详情与动作仍以服务端返回的对象 capabilities 为准并在提交时重验。
- 数量角标不是导航能力本身。入口可见但指标不可用时显示“暂不可用”，不能显示零或从其他组织总量推算。

### 5.2 Dashboard 与队列下钻

- Dashboard 响应按卡片返回 `metricCode/value/asOf/availability`，顶层返回 `scopeDigest` 和口径版本。个人、团队、SLA、审批和运营指标各自使用批准的范围化只读查询；不支持的组合明确不可用。
- 卡片下钻只携带稳定筛选编码，不携带组织范围或授权谓词。列表服务以当前主体重新解析范围，数量与列表采用相同口径；`asOf` 或范围摘要变化时提示刷新。
- 聚合超时或数据源失败可部分返回，但失败卡片不得伪造值、泄露内部 SQL/服务地址或阻断安全的其他卡片。

### 5.3 草稿、表单 Schema 与步骤

- 浏览器草稿白名单只包含非敏感输入、目录/系统编码、当前 `stepCode` 和 `formSchemaId@version`；附件、token、Cookie、CSRF、幂等键、内部评论、候选目录和授权上下文禁止落浏览器持久存储。
- 服务端草稿与临时附件分离：草稿保存临时附件 ID，不保存内容或下载 URL；附件仍位于隔离区。草稿读取、更新、提交均校验主体、范围、schema 和乐观版本，并受 TTL 控制。
- schema 步骤元数据只表达顺序、字段集合、完成条件和帮助信息，不表达可执行脚本或流程跳转。最终提交由服务端按冻结 schema 校验，前端隐藏字段和跳步不能绕过必填、范围或敏感字段规则。

### 5.4 目录—流程发布包草案

- 每个已发布目录版本必须唯一映射 `formSchemaId@version`、已部署 BPMN/DMN 定义 ID/版本、首节点路由策略和 SLA 版本；建单时将该组合冻结到工单/流程快照。
- 发布包草案记录上述引用、兼容说明、校验结果和复核事实，按 `DRAFT/VALIDATED/PUBLISHED/RETIRED` 管理。发布后不可编辑；退役只阻止新建，不改变历史工单和活动流程。
- 首批后台只选择已经由受控流水线部署和登记的资源，不提供 BPMN/DMN/schema 文件上传、在线低代码设计或动态脚本入口。

## 6. 验收要点

- 同一系统下只返回已发布、活动模块；跨系统模块或目录映射被篡改时拒绝。
- 系统/模块退役后不可新建，但历史工单仍显示冻结快照。
- 系统级与模块级目录映射按确定优先级解析，不能出现多默认歧义。
- 未经授权者不能读取其他组织的系统、模块、候选人、协办人或路由策略。
