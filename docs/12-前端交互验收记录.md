## 工单处理页截图对齐验收

本批修改已有工单的处理/详情工作区，不改变新建页单页布局。左侧连续展示基础资料、处理意见和解决信息；右侧集中状态/SLA、可检索的知识、人员和内部沟通；关联/审批/协作/流转历史保留为页签，底部操作仅采用服务端返回的动作与禁用原因。

实测结果（写入均由 `frontend/tests/browser-processing-fixture.js` 模拟接口拦截）：

| 检查 | 结果 |
| --- | --- |
| 取消保存处理意见 | 写请求 0；处理意见、解决说明都保留 |
| 评论接口 500 | 原文保留，页面未回显注入的内部错误信息 |
| 评论成功 | 请求使用 INTERNAL_COMMENT/comment 和 If-Match；右侧显示记录，只清处理意见，保留解决说明 |
| 解决动作 | 类别、正文与弹窗补充完整拼入 RESOLVE reason，携带版本，不发送 HTML；显示待审批而非已解决 |
| 未保存时切单 | 取消离开则仍在原单且原文保留；确认离开后新单无旧正文 |
| 只读工单 | 可编辑正文数量 0、底部写按钮数量 0，没有新增请求 |
| 知识区 | 已授权发布条目显示，可搜索；修复空关键词被拼接空格误判为无结果的问题 |

| 新建页回归 | 主题/页签/提交入口正常，原图片按钮保留，处理区才禁用图片 |

当前 `npm test` 共 13 项通过：6 项处理文本/长度/不消费草稿行为、5 项建单提交会话、2 项审批结果映射。生产构建与差异检查通过。另以真实本地接口只读打开既有工单，未修改任何真实工单；实际保存结果不以模拟验证替代生产联调。

范围边界：当前处理接口保存纯文本，编辑排版不持久化；处理意见最长 2000 字符，解决依据（含类别与补充）最长 1000 字符。截图中的不受现有接口支持的可编辑优先级、实际解决时间等未伪造保存。只有真实记录原因的动作才消费处理草稿，其余动作明确保留未提交内容。候选人异步请求使用弹窗序号隔离，切单/身份变化和卸载使旧结果失效。

## 可复执行的自动测试

在 `frontend` 下使用 Node.js 24 执行 `npm test`。提交会话测试共 5 项：

1. 同时确认共用一个在途 Promise；成功后复用已有工单结果。
2. 结果不明后保持原请求 JSON 与幂等键，后续表单/传输层修改不污染原请求。
3. 首次明确拒绝后可纠正内容并使用新键。
4. 在途或成功后不能释放提交意图。
5. 未知结果 → 403 → 成功全过程仍为同键、同内容。

## 已知恢复边界

- 提交请求/幂等键及文件进度只保存在本页内存，不持久化业务正文。刷新/关闭后不会自动重放，应先去工单中心核对。
- 结果不明的文件不自动重传，以免服务端已接收而重复上传；用户需在原单查看附件后补齐缺失文件。
- CLEAN 图片才尝试关联正文；关联冲突或失败不回滚主单、不重传已成功文件，回执提示到原单核对。
- 未知创建后的任意后续拒绝都不能证明首次未成功，因此不能释放原幂等键。
