# 内网 IT 工单系统需求规格说明书

## 1. 目标与边界

系统为内网普通用户和 IT 服务团队提供统一服务台，处理页面卡顿、系统故障、账号权限、软件安装、网络、设备和一般服务请求。目标是提高受理可见性、缩短恢复时间、建立可审计的处理协作和可复用的知识沉淀。

不在当前项目范围：浏览器端性能采集软件、AI 自动生成知识正文或自动理解能力、对 IAM 主数据的编辑、CMDB 主数据维护。系统通过接口关联已有平台能力。

## 2. 角色与权限

| 角色 | 主要权限 |
| --- | --- |
| 提单人 | 提交、补充、撤销本人未受理工单；查看本人及被授权范围的进度、评价与知识文章 |
| 一线支持 | 服务目录受理、抢单、分类、初步诊断、转派、协办、处理及知识候选提交 |
| 二线支持 | 处理专业队列、高风险变更审批前技术评估、并行子任务与根因补充 |
| 主办人 | 对处理结果负责；统筹协办和子任务；发起升级、挂起和关闭申请 |
| 协办人 | 处理被分配的协作事项，提交结果、附件和内部评论；不越权关闭主单 |
| 审批人 | 按流程策略审批指定的状态转换和会签任务；仅见与职责范围相关数据 |
| 主管/服务经理 | 队列、SLA、升级、人员工作量、报表和委派管理 |
| 平台管理员 | 服务目录、流程版本、权限策略、IAM 映射、字典、集成与审计查询；不可篡改审计记录 |

权限采用 RBAC（岗位角色）+ 数据范围（组织、服务、队列、CI）+ 委派规则组合。默认拒绝，所有越权访问记入审计。

### 2.1 集团数据隔离与队列授权

集团内组织、区域公司和专业支持组共享同一平台时，角色本身不授予集团全量数据。对象读写权限必须同时满足：当前角色允许该动作、至少一个有效数据范围命中工单的组织/服务/队列/CI、对象密级允许当前主体访问。平台管理员、服务经理和审计员也必须具有明确数据范围；禁止因“管理员”角色自动获得集团全量工单正文、附件或统计数量。

- 列表、详情、数量、聚合、搜索建议、导出和消息待办使用相同的数据范围谓词；不能先查询全量数据再由浏览器或内存代码过滤。
- 组织树范围必须使用不可变 IAM 组织 ID 计算，不能以组织名称、前缀或客户端提交的父子关系判断。组织调整不改写历史身份快照，但当前访问权限每次按最新有效授权重算。
- 服务、队列和 CI 范围均为独立授权维度。同一类型的多个范围值取并集，同一个授权包中不同类型取交集，再与角色动作能力取交集；禁止把“组织 A + 服务 B”拆成“组织 A 全部服务或服务 B 全部组织”。现有扁平授权在迁移为显式授权包前统一视为一个授权包，任何未命中维度默认拒绝。
- 跨组织协办、交接、转派或审批只为被指派主体授予完成该对象任务所需的最小权限，不扩展其对来源组织其他工单、队列数量或人员名单的访问。协作结束、任务失效或授权撤销后，临时对象权限随之失效，已产生的审计与身份快照保持不可修改。
- 所有拒绝响应使用统一安全摘要，不返回对象是否存在、所属组织、队列人数、总量差异或候选身份；越权尝试记录主体、对象、动作、请求关联 ID 和拒绝原因码。

## 3. 功能需求

### 3.1 工单与服务目录

- 服务目录可配置工单类型、必填字段、优先级、默认队列、流程版本和审批策略。每项服务还必须指定服务负责人、支持组、服务时间、数据密级、SLA 策略和下线日期。
- 平台提供受控低代码配置：服务目录、表单字段与分组、联动/校验规则、标签、路由、审批、SLA/OLA、通知模板、流程事件和报表模板均通过元数据配置、版本化发布和回滚实现。表达式只允许使用白名单变量和函数，禁止配置任意脚本、SQL、文件路径或外部网络请求。
- 一期将运行对象区分为：事件（Incident，恢复非预期服务中断或性能下降）、服务请求（Request，标准服务交付）、权限申请（Access Request，受控授权）、问题（Problem，根因和已知错误）与变更（Change，受控技术变动）。问题和变更一期可先作为关联对象和受控入口，但不得用普通工单的关闭规则替代审批。
- 每张工单拥有稳定编号、来源、影响范围、紧急度、优先级、服务/CI、状态、时间线、附件、订阅人和关联记录。
- 支持模板、草稿、批量导入、相似工单提示、合并/拆分与父子工单。
- 建单表单遵循“结构化优先、自然语言补充”原则：服务目录为每种请求提供标准选项、必填字段和动态校验；文本描述仅用于补充上下文。页面卡顿至少使用业务系统、功能/页面、环境、发生时间、影响范围、现象、频率、已尝试操作等结构化字段。
- 支持标准标签和自由标签。标准标签由服务目录、CI、告警、规则或人工选择产生；自由标签采用 `#标签名` 形式，例如 `#核协E`、`#扫码`，需记录来源、创建人、适用范围和审核状态，不能作为唯一的授权、审批或 SLA 判断依据。
- 用户提交前，系统以结构化字段、标签和脱敏文本检索已解决工单与已发布知识，返回相似度、适用范围、解决摘要和跳转链接；用户可“按指引自助解决”“仍需提交”或“反馈不相关”。
- 页面卡顿工单应至少包含：业务系统、页面/URL 标识、发生时间窗、用户网络/终端摘要、影响范围、性能采集会话 ID、采集报告地址、APM Trace/事务 ID、日志检索链接和脱敏说明。
- **服务系统注册与模块联动：** 影响系统必须从已发布服务系统注册中心选择，而不是普通全局字典。每个系统维护可用模块/页面、只读 CI 关联、可发起服务目录和目录节点路由；模块级映射优先于系统级映射。提单时固化系统、模块、目录与注册版本快照，后续注册变更不改写历史工单。

#### 3.1.1 附件扫描状态与用户体验

附件和知识源文件上传后必须先进入服务端隔离区，状态只能由受管扫描流程更新，浏览器、文件名、扩展名和请求 `Content-Type` 均不能声明扫描结论。统一扫描状态为：

| 状态 | 含义 | 用户可执行能力 |
| --- | --- | --- |
| `QUARANTINED` | 文件已接收并隔离，等待扫描或重试扫描 | 可查看脱敏元数据和进度；不可下载、内联预览、解析、索引或发布 |
| `CLEAN` | 受管扫描器确认通过，且服务端内容类型/大小策略通过 | 仍需对象权限校验后才可下载或预览；知识版本满足其他审核条件后才可发布 |
| `REJECTED` | 检出恶意内容、禁止类型或不可接受内容，属于最终拒绝 | 不可下载、预览、解析、索引或发布；展示安全原因摘要，可删除/重新上传新文件但不能重试原内容绕过拒绝 |
| `SCAN_FAILED` | 扫描器不可用、超时或内部错误，无法形成安全结论 | 不可下载、预览、解析、索引或发布；服务端可按策略受控重试，不能降级为通过 |

允许的主转换为 `QUARANTINED -> CLEAN | REJECTED | SCAN_FAILED`，以及 `SCAN_FAILED -> QUARANTINED` 后重新扫描。任何未知状态、缺少扫描记录、扫描结果签名/来源不可验证或状态冲突均按非 `CLEAN` 处理；禁止通过数据库手工改状态、客户端回传状态或扫描服务故障时“临时放行”。

- 下载、正文内联图片、知识预览、文本抽取、案例匹配和知识发布必须在各自操作时重新读取最新扫描状态并执行对象授权，不能信任上传响应或浏览器缓存中的旧 `CLEAN`。
- `SCAN_FAILED` 重试必须由服务端返回能力，校验当前对象权限、文件仍在隔离区、重试次数/退避窗口和扫描器健康状态；使用稳定附件 ID、幂等键和乐观状态条件，记录尝试次数、触发人、原因、扫描器结果摘要和审计。并发重试只能有一个扫描任务生效。
- 达到最大重试次数、文件缺失、哈希变化或扫描器仍不可验证时保持 `SCAN_FAILED` 并转人工处置；不能伪造 `CLEAN`、重新命名文件或复制为新附件绕过门禁。`REJECTED` 不提供原文件扫描重试。
- 页面在上传完成后必须明确显示“已隔离待扫描”，按服务端状态轮询/刷新；为四种状态提供不同标识、解释和下一步。非 `CLEAN` 不渲染下载/预览链接；只有服务端返回可重试能力时显示“重试扫描”，提交后防重复点击并展示尝试结果。
- 工单先创建、附件后上传时，附件扫描失败不得把工单显示为提交失败或诱导重复建单。页面应保留工单编号，逐附件展示状态，并允许在原工单上恢复受控上传/扫描；正文待上传图片在 `CLEAN` 前保持安全占位，不生成可访问 URL。

#### 3.1.2 完整建单工作区与草稿恢复（截图反馈修订）

**最新用户确认：取消三步向导，以用户提供的第二张截图为布局基准。此修订优先于本文及其他历史记录中的三步要求。** 新建页同屏展示主题、基础信息/关联工单/流程图页签、IAM 申请人信息、系统/模块/目录、动态业务字段、富文本、附件列表；右侧展示工单概况、时效状态、知识建议和标签。主操作为底部“提交工单”，提交前使用确认弹窗，不通过步骤隐藏主体内容。保留防重复提交、未知结果同键重试、附件回执、权限和安全草稿边界。

新单尚不存在时，编号、流程实例、SLA 截止时间、处理人、协作记录展示“提交后生成/暂无”，不得复制参考图中已有工单的真实状态或时间。无独立新建接口的关联操作展示其创建后入口和说明，不实现假按钮。全局原生 input 样式不得覆盖 Element Plus 内部输入框；选中标签、搜索文字、光标和边框必须正常显示。

新建工单面向普通用户固定为三个主步骤，复杂目录仍通过步骤内分组和条件字段扩展，不能把后台流程配置直接暴露给请求人：

1. **选择服务：** 搜索或按系统/分类选择已发布服务目录，展示服务摘要、预计处理流程和所需材料；系统、模块和目录联动在本步完成。
2. **填写信息：** 按“基本信息、影响与紧急程度、问题/诉求说明、附件”分组呈现当前表单版本字段；条件字段只在触发条件满足时出现，并就近说明出现原因。
3. **确认提交：** 汇总服务、组织、关键字段、可见附件状态和提交流程；用户返回前一步不丢数据，最终一次确认才创建工单。

- 页面自动保存安全草稿：字段有效变化后 2 秒防抖写入当前标签页的 `sessionStorage`，草稿绑定当前 IAM 用户及组织、服务目录和表单版本，最长 24 小时过期。首期仅保存系统/目录选择及表单明确标记为非敏感的布尔、枚举和日期选项；主题、自由正文、自定义标签、密码/令牌、附件及其文件名、Blob/Base64、候选人和授权元数据只留在内存，不得持久化；退出登录、身份切换和用户主动删除时清理。
- 服务端草稿属于后续能力，接口未交付前页面必须明确标注“仅保存在当前浏览器”，不能宣称已跨设备保存。未来服务端草稿仍须对象授权、版本、加密、审计和保留期，并与本地草稿以服务端版本/更新时间对账，禁止静默覆盖较新内容。
- 页面发现匹配的未过期草稿时显示非阻断恢复提示，包含服务名称、保存时间、当前/草稿表单版本和“恢复、放弃”操作；不得静默恢复。表单版本变化时只恢复仍兼容字段，列出未恢复字段并要求用户确认。
- 字段校验实时但不打扰：首次离开字段或用户尝试下一步/提交后才显示错误；输入过程中采用不少于 300 毫秒防抖，不弹窗、不连续抢焦点。条件隐藏字段不提交，也不以隐藏错误阻断；再次显示时重新校验。
- 提交失败在页首提供错误摘要和请求关联 ID，并在摘要中链接到对应字段；首个可修复错误在 100 毫秒内滚动并聚焦。服务端错误是最终依据，不能只显示“提交失败”或要求用户从头填写。
- 工单已创建但附件上传/扫描失败时进入“主单已成功、附件待恢复”结果页，显示工单编号和逐附件状态，可在原单继续上传/重试扫描；不得自动再次创建工单。
- 页面存在未保存变化、待上传附件或未确认恢复草稿时，站内路由离开和浏览器关闭应提示；没有变化、已完成本地保存或已提交成功时不误报。提示不得阻止用户明确放弃。
- 三步流程必须支持完整键盘操作、清晰焦点顺序、可访问错误关联和移动端单列布局。Enter 不得在多行文本、标签或中间步骤意外提交；最终提交使用独立按钮并防重复点击。

### 3.2 状态与默认审批策略

状态集合：草稿、已提交、待分类、待分派、待受理、处理中、已解决、待用户反馈、已关闭、已撤销、已挂起。升级是独立的协同/可见性标记与升级记录，不作为替代主状态的终态。

| 转换 | 默认执行者 | 默认审批 | 说明 |
| --- | --- | --- | --- |
| 提交 -> 待分类 | 提单人 | 可配置 | 服务目录校验后进入队列；高风险服务可启用受理前审批 |
| 分类/分派/受理/处理中 | 服务台或处理人 | 可配置 | 默认快速处置；目录可对指定转换启用单人、会签或或签审批 |
| 转派、协办、并行子任务 | 主办人或有范围权限者 | 可配置 | 记录原因、接收方和前后责任人；高影响事件可要求主管确认 |
| 处理中 -> 已解决 | 主办人 | 可配置 | 必填解决方案、验证证据和知识候选；高影响事件可要求关闭前会签 |
| 已解决 -> 待用户反馈 | 系统 | 否 | 通知提单人，等待用户确认或在目录定义的观察期内复核 |
| 待用户反馈 -> 已关闭 | 系统/提单人/服务台 | 可配置 | 用户确认或超期自动关闭；自动关闭前须提醒并允许补充 |
| 重开 -> 处理中 | 提单人或服务台 | 可配置 | 保留原解决方案与 SLA 规则；重开原因、次数和时限受目录控制 |
| 挂起/恢复、升级/解除升级、撤销 | 有范围权限者 | 可配置 | 挂起仅使用允许原因；审批、SLA 暂停和通知按策略在执行时计算 |

审批策略按“服务目录 + 优先级 + 风险标签 + 状态转换”配置，可选择单人、会签、或签、逐级审批、超时升级和审批人代理。

流程支持**受控跳转**：流程负责人或经双人审批授权的平台管理员可将运行实例纠偏至已定义的目标节点。跳转前必须完成权限校验、目标节点白名单、必填字段校验、未完成任务处置、候选人重新计算、SLA 影响预览与通知预览；跳转原因、前后节点、操作者、审批人、实例版本和影响任务以不可修改事件记录。禁止跳过身份授权、高风险变更、关闭会签等硬性控制节点；禁止通过直接更新状态字段、流程表或数据库实现跳转。

### 3.3 多人协作

- 抢单采用原子领取：同一时刻只允许一位合资格人员成为主办人；失败者得到当前责任人提示。
- 主办人可添加协办人，协办任务有独立待办、期限和结果，主单仍由主办人推进。
- 并行工作使用子工单或 BPMN 并行任务；汇聚条件可配置为“全部完成”“任一完成”或“达到法定人数”。
- 会签支持指定人员、角色池、组织主管链和动态规则；审批快照固定审批人集合，组织变动不应改变进行中的责任归属。
- 交接班必须记录交接说明、未完成事项、附件、接班人确认和时间；交接后新主办人承担后续 SLA。
- 内部评论仅处理团队及授权主管可见；对用户公开的回复必须明确标记。所有评论、状态和责任变动生成不可修改的时间线事件。
- 待办处理采用左侧处理表单、右侧协作沟通区；右侧展示主办/协办、内部评论、交接/转办、抢单和流程/SLA 摘要。协办入口与候选人只能由服务端按当前对象权限和角色池返回。

#### 3.3.1 个人队列与团队队列

队列是服务责任边界，不等同于 IAM 组织，也不能由浏览器临时拼接。平台必须同时提供个人工作视角和经授权的团队工作视角：

| 队列语义 | 包含范围 | 可执行主体 |
| --- | --- | --- |
| 我的待办 | 当前用户已指派、已领取或作为有效候选人的活动任务 | 当前用户 |
| 团队未领取 | 当前用户获授权团队中尚无主办人、允许共享领取的活动任务 | 合资格候选人可原子抢单；队列主管可受控分派 |
| 团队处理中 | 当前用户获授权团队负责且已有主办人的未完成工单 | 主办/协办按对象能力处理；队列主管按范围监督 |
| 团队临近违约 | 上述团队工单中 SLA 风险为临近违约 | 主办人与队列主管优先处置 |
| 团队已违约 | 上述团队工单中 SLA 已违约 | 队列主管、服务经理按升级规则处置 |
| 待交接 | 当前用户需确认接班，或其管理团队存在未完成交接 | 指定接班人确认；队列主管只处理服务端授予的管理动作 |

团队队列必须由服务端返回当前主体可选的稳定队列编码、展示名称和能力；客户端只能选择服务端已授予的队列，不能提交任意组织、人员、角色池或处理组扩大结果集。普通提单人默认不获得团队队列；一线/二线支持只看到其活动支持范围；队列主管只看到明确管理的队列；平台管理员若无相应数据范围也不能查看队列内容。

#### 3.3.2 数据库稳定分页与筛选

- 工单列表必须在数据库查询阶段完成对象授权、队列语义、关键词、状态、类型、优先级、服务目录、影响系统、申请组织、SLA 风险和日期范围过滤，再执行排序与分页；禁止只取固定首批记录后在前端进行“当前页筛选”。
- 核心待办列表采用不透明游标分页。默认每页 20 条，可选择 20、50 或 100 条；响应返回当前查询快照、下一页游标和是否有更多数据。游标必须绑定当前 IAM 主体、授权版本、队列、筛选条件、排序字段和快照时间，不能跨用户或修改条件后复用。
- 第一批默认排序为“创建时间倒序、工单稳定编号倒序”，只使用不可变键保证查询快照稳定。后续如增加最后更新时间、SLA 风险等可变排序，必须另行定义快照语义、专用索引和游标版本；所有排序始终追加稳定编号作为唯一决胜键。
- 同一查询快照内翻页不得重复或跳过未变化记录。翻页过程中新增或更新的工单在主动刷新后进入新快照；权限被撤销的对象必须立即停止返回，安全性优先于凑满页大小。
- 总数仅在业务页面确有需要且当前主体有权获知时返回，并使用与列表完全相同的授权与筛选谓词。不能通过总数、空页、排序差异或响应时间推断无权组织的数据。
- 查询条件必须参数化，关键词长度、日期跨度、页大小和排序字段均由服务端限制；常用队列与排序组合应建立可验证的数据库索引，不允许以加载全量记录到应用内存替代数据库分页。

#### 3.3.3 团队队列配置与主管工作台

团队队列是受版本和数据范围治理的服务对象，至少包含稳定队列编码、名称、归属组织 `owningOrganizationId`、服务目录范围、可选系统/CI 范围、支持角色、分派模式、共享领取开关、容量阈值、升级链、主管成员、普通成员、有效期、状态和版本。队列编码创建后不可变，浏览器不能提交或修改成员的 IAM 角色、组织和数据范围。

- 队列成员必须引用启用的 IAM 用户，并记录成员类型（普通成员/队列主管）、生效时间、失效时间和配置版本。普通成员只获得候选/领取资格；队列主管获得当前队列的监督、受控分派、回收和升级能力，但仍需命中工单对象数据范围。
- 队列范围按归属组织与服务目录取交集；可选系统/CI 只能进一步收窄，不能扩大组织和目录范围。激活队列必须至少有一个有效服务目录、一个活动成员和一个活动主管；范围为空、目录失效或 IAM 投影不可验证时关闭式失败。
- 共享领取只能在已发布节点策略和活动队列同时允许时生效。领取人必须为当前有效成员、命中工单目录/系统/CI 范围、未超过容量并持有节点候选角色；领取使用工单版本和唯一活动主办约束保证原子性。
- 停用队列后不再接收新路由、不出现在新建配置和可领取队列目录中。停用前必须选择替代队列并预演影响；未领取任务原子迁移到替代队列，已在办任务默认保留原责任快照并由主管逐单交接，禁止静默清空责任人或重置 SLA。
- 主管工作台至少展示当前授权队列的未领取、处理中、临近违约、已违约、超容量、长时间无更新和待交接数量、成员负荷及下钻入口。数量、成员负荷和下钻列表使用同一数据范围与查询快照；主管不能通过工作台读取未授权队列或其他组织人员负荷。
- 队列新增、成员变更、范围变更、共享领取开关、容量、主管和停用/迁移均需变更原因、乐观锁和不可修改审计；影响进行中任务的变更必须先预演并明确生效边界。

##### 队列写操作幂等

团队队列后台所有写操作，包括创建、更新、成员/主管变更、范围变更、激活、停用计划创建、计划提交审批、审批决定、执行、失败项重试和取消，均必须携带 `Idempotency-Key`。服务端以“当前 IAM 主体 + HTTP 方法 + 规范化资源/动作 + Idempotency-Key”定位幂等记录，并保存规范化请求指纹、处理状态、响应摘要、资源版本和审计事件引用。

- 同一个键和同一个请求指纹重放时，返回首次请求的等价状态码与结果引用，不重复创建队列/计划、迁移任务、交接任务、流程实例、通知或审计业务事件。
- 同一个键对应不同请求指纹时返回 `409 Conflict`，不执行新请求，也不以新请求覆盖原幂等记录。指纹至少覆盖路径资源、期望版本、原因、范围/成员变更、替代队列、计划 ID 和执行动作。
- 幂等键不能绕过对象权限、数据范围、CSRF、状态机和乐观锁。首次执行仍须完成全部校验；已完成请求重放返回原结果，尚未提交任何副作用的可重试失败允许使用同键继续，进入未知/执行中状态时客户端必须先查询状态而不能换键盲目重试。
- 幂等记录保留期必须覆盖浏览器、网关和异步执行的最大安全重试窗口。服务端日志不得记录完整幂等键或请求敏感正文，只记录不可逆摘要和请求关联 ID。

幂等记录处于 `IN_PROGRESS` 时必须可查询，并返回资源/计划 ID、状态、首次接收时间、最近心跳时间、租约到期时间和安全重试建议，不返回 HMAC、规范化正文、执行节点内部地址或敏感错误。客户端遇到超时、连接中断或 `IN_PROGRESS` 时只能使用原 `Idempotency-Key` 查询/重放原请求，或按已返回的资源/计划 ID 查询状态；禁止更换键盲目重试同一业务意图。

- 执行权使用带版本的短期租约，记录执行节点标识摘要、租约令牌摘要、`leaseExpiresAt` 和心跳。租约未过期时其他节点只能返回当前 `IN_PROGRESS`；租约过期后，另一个节点可通过数据库比较并交换原子接管，原节点的旧租约不得继续写结果。
- 接管或重试前必须先按队列编码、计划 ID、计划项自然键、业务结果引用和审计关联进行对账。若业务对象、迁移事件或交接待办已经成功存在，应优先把幂等记录补记为 `COMPLETED` 并返回原结果，禁止再次执行业务写入。
- 对“业务事务已提交、幂等完成状态尚未写入”这一崩溃窗口，业务写入必须保存幂等记录 ID/操作自然键，或二者在同一事务内建立唯一关联。恢复逻辑先确认既有结果的请求指纹和主体/资源绑定一致，再完成幂等记录；无法安全对账时保持受控失败并人工处理，不得猜测失败后重新执行。
- 请求指纹由服务端对规范化方法、路径、资源、期望版本和受控请求体计算 HMAC，客户端不生成、不提交、不可见。服务端使用受管密钥和常量时间比较，幂等记录保存密钥版本而非明文密钥；日志和响应不返回指纹/HMAC。
- 密钥轮换后，新记录使用当前版本，保留期内旧记录仍以其固化密钥版本验证和重放。轮换不得使同键同请求变为冲突、使异请求通过或导致重复执行；旧密钥不可用且无法验证时关闭式阻断并先对账，不能降级为普通哈希或跳过指纹校验。

##### 历史幂等记录升级语义

在服务端 HMAC 指纹、密钥版本、租约或业务结果唯一关联上线前创建的历史幂等记录，不得补算一个未经证明的指纹，也不得继续自动重放或接管执行。历史记录只能进入以下用户可见状态之一：

| 状态 | 判定条件 | 用户语义与处置建议 |
| --- | --- | --- |
| `LEGACY_RESULT_ONLY` | 已通过业务自然键、资源版本和审计关联确认结果真实存在，但无法按新 HMAC 规则验证原请求 | 仅返回已验证的安全结果引用；禁止再次执行业务。提示“历史请求已产生结果，请使用现有结果” |
| `RECONCILIATION_REQUIRED` | 无法确认业务是否提交、结果归属或原请求指纹，或旧执行状态停在处理中且没有可信租约 | 不自动重放、不自动失败；提示“结果不确定，请保持原 key 并联系有权人员对账”，返回人工处置单/支持引用 |
| `FAILED_FINAL` | 已确认业务未成功且该历史请求不满足安全自动重试条件，或人工对账认定不可恢复 | 不自动重试；提示最终失败原因摘要和重新发起业务的受控指引。重新发起必须由用户明确确认是新的业务意图，不能由客户端自动换 key |

- 客户端查询到上述任一状态均不得用新 `Idempotency-Key` 自动重试原业务。`RECONCILIATION_REQUIRED` 尤其不能以“查不到结果”等同于失败；用户只能查询原 key 或使用返回的人工处置引用。
- 历史 key 再次提交到原写接口时，服务端返回对应历史状态和状态查询/结果引用，不进入当前自动重放执行器。未知或其他主体的 key 仍按防枚举策略处理。
- 人工对账必须由具备队列管理角色和相应 `DATA_SCOPE` 的人员处理，记录证据、结论、操作者、复核人和审计事件。处置可把记录归结为 `LEGACY_RESULT_ONLY` 或 `FAILED_FINAL`，但不得伪造原 HMAC、改写原业务事件或删除不确定性证据。
- 管理 UI/SDK 必须明确区分“历史结果仅可使用”“需要人工对账”“最终失败”，展示安全处置建议和支持引用，不提供“强制重放”“换 key 再试”按钮。

##### 队列停用计划与可恢复执行

停用队列不能由单个同步请求直接改状态。服务端先创建不可变的停用预演计划，冻结源队列编码/版本、替代队列、原因、申请人、组织与目录范围、查询快照、未领取任务清单、在办交接清单、阻断项、SLA/通知影响和逐项版本。计划状态至少包含：草稿、预演失败、待审批、已批准、执行中、部分完成、已完成、失败、已失效和已取消。

- 预演逐项判断任务仍存在、源队列/工单版本一致、替代队列范围兼容、目标容量和候选人可用。存在无替代范围、越权对象或硬性阻断项时不得提交审批或执行。
- 审批只针对被冻结的计划版本；申请人不得自审。源/目标队列、组织范围、任务版本或审批策略变化时计划失效，必须重新预演，不能在旧批准结果上替换清单。
- 执行先原子保留计划，防止并发执行。未领取任务按清单逐项迁移到替代队列；已有主办的在办任务不静默迁移责任，而是生成明确的交接待办清单，保留主办人与 SLA 连续性。
- 每个计划项具有稳定项 ID、期望版本、执行状态、尝试次数、结果码和审计引用。批次失败后只重试未执行或可重试失败项；已成功项重放必须返回原结果，不重复迁移、交接、通知或审计。不可重试失败使计划保持部分完成/失败并要求主管处置，不能把队列错误标记为已完全停用。
- 队列只有在所有未领取迁移项成功、所有在办项已生成有效交接任务且无阻断项时才进入停用状态。网络超时后客户端先查询计划和逐项结果，不能依据 HTTP 超时推断失败或另建计划。
- 管理 UI 必须展示计划版本、状态、审批状态、影响摘要、阻断原因及可分页的逐任务结果；只对服务端返回为可重试的项目提供重试入口，并在执行期间禁用重复提交。本批可先交付 API 与状态模型，但正式开放停用按钮前必须完成上述展示。

#### 3.3.4 角色默认工作台与真实状态

登录后的默认工作台由服务端当前角色、队列关系和数据范围生成，用户只能在已授权视图中选择个人偏好；偏好不构成权限，也不能让角色切换后继续打开已失权视图。

| 主体 | 默认视图 | 首要信息 |
| --- | --- | --- |
| 提单人 | 我发起的服务 | 处理中、待补充、已解决待确认、最近知识 |
| 一线支持 | 我的待办；有资格时并列团队未领取 | 待受理、SLA 风险、共享领取和下一动作 |
| 二线支持 | 我的专业待办与授权团队处理中 | 专业协办、待交接、阻塞和解决目标 |
| 队列主管 | 授权团队风险工作台 | 未领取、临近/已违约、超容量、停滞、待交接与成员负荷 |
| 服务经理 | 服务运营工作台 | 目录/系统分布、队列风险、重大事件、改进项和下钻 |
| 审计员 | 授权范围只读审计视图 | 审计事件、版本和导出，不显示任何写动作 |
| 平台管理员 | 配置治理入口 | 配置健康和发布待办；没有业务 DATA_SCOPE 时不展示集团工单汇总 |

工作台必须区分真实空、错误、延迟和部分可用状态：

- **真实空：** 仅在服务端成功返回且授权范围内确为零时显示，说明当前筛选/范围并提供合理下一步；禁止以空态掩盖 403、超时或接口失败。
- **错误：** 显示受影响模块、脱敏错误摘要、请求关联 ID 和重试；保留旧数据时必须明确标记“上次成功数据”，不能继续当作实时值。
- **延迟：** 所有运营数字显示 `asOf`/最后更新时间；超过口径定义的新鲜度后标记“数据延迟”，不能用“整体平稳”、绿色状态或 0 替代未知。
- **部分可用：** 卡片独立展示可用/不可用，页面总体可继续使用；不可用卡片不参与合计或健康结论。数量卡片下钻必须与相同授权、筛选和快照一致。
- 首页不得包含硬编码业务数量、重大事件、班次、服务健康或推荐知识；所有事实必须来自服务端读模型或明确标记为演示数据。

### 3.4 集成、知识与报表

- 告警按来源系统、告警指纹和时间窗去重，可自动生成或关联工单；必须支持人工确认和关闭回写。
- CMDB 用服务和 CI 编码关联影响对象；CMDB 不可用不得阻塞人工建单。
- 日志/APM 提供深链接和关联标识；查询凭证由平台侧单独鉴权，不将日志正文批量复制进工单。
- 知识库支持 Markdown/HTML、分类、标签、版本、审核状态、导入、附件和工单关联；当前不接入 AI 生成或自动发布能力。
- 报表覆盖工单量、类型、SLA、首次响应、解决时长、重开率、积压、人员负荷、系统/部门分布、重复问题、知识命中率、重大事件恢复时长、告警噪声率和通知送达率。

#### 3.4.1 知识归属、目录范围与数据隔离

每个知识文档必须固化 `owningOrganizationId` 和非空的 `serviceCatalogItemIds`；每个版本保存发布时的归属组织、服务目录集合、来源类型、来源工单、创建人和审核快照。已发布版本不可原地修改归属或目录，调整必须创建新草稿、重新审核并发布。

- 普通用户只能检索和阅读 `PUBLISHED` 状态、`owningOrganizationId` 等于当前 IAM 组织且至少一个 `serviceCatalogItemId` 位于其可见目录范围内的内容。当前组织无法从可信 IAM 会话解析、目录集合为空或目录已失效时不返回知识正文、摘要、数量或附件。
- 知识管理动作必须具有 `ROLE_SERVICE_MANAGER` 或 `ROLE_PLATFORM_ADMIN`，并命中 `DATA_SCOPE_ORGANIZATION:<owningOrganizationId>`；平台管理员也不因角色自动获得跨组织正文、版本或审核权。`ROLE_AUDITOR` 仅可在数据范围内只读审计元数据。列表、详情、版本历史、审核队列、正文预览、附件、复审候选和反馈使用同一授权谓词。
- 从已解决/关闭工单创建知识草稿时，服务端从工单冻结快照继承 `owningOrganizationId` 与 `serviceCatalogItemIds`，浏览器不能覆盖。来源工单缺少可信组织或目录快照、当前主体无源单读取权或无目标组织管理范围时关闭式失败。
- 导入知识时，`owningOrganizationId` 只能由服务端当前 IAM 主组织确定；浏览器仅能从服务端返回的授权目录中选择 `serviceCatalogItemIds`。服务端重新校验目录已发布、属于当前组织可管理范围且集合非空，不能以请求体组织 ID、文件目录名或标签推断归属。
- 反馈提交前重新校验当前用户对指定已发布版本的读取权；反馈汇总、列表计数和复审触发同样按组织与目录范围过滤，不能借由反馈数量推断其他组织存在同名知识。
- 旧知识迁移不得默认归入平台组织或开放为全局内容。缺少可信组织/目录的记录进入只可审计的 `MIGRATION_PENDING` 状态，在完成受审计映射、冲突校验和抽样复核前不得检索、预览、审核、反馈或发布。

### 3.5 规则分流与案例推荐

- 当前采用规则分流：服务目录、结构化字段、标签字典、CI、错误码与关键词精确匹配已发布知识和已解决案例；不接入 AI、模型或语义检索。
- 匹配结果必须展示证据：命中的字段、标签、案例状态、适用服务/CI 和最近复审时间。知识已废弃、无访问权限或数据密级不匹配时不展示正文。
- 标签、关键词、错误码、同义词、服务映射和排序权重均由平台管理员通过字典维护，支持模板导入、校验、版本发布与导出；字典修改必须审计并可回滚。
- 必须记录规则版本、命中证据、采纳/忽略/不相关反馈、最终分类和最终解决结果，用于评估命中率、自助解决率、错误分派率和人工介入率。

## 4. 非功能需求

- 在峰值 1,000 并发下，核心列表和详情接口 P95 小于 2 秒，建单/状态变更 P95 小于 3 秒；不含外部平台响应。
- 关键功能 7x24 运行；应用任一节点失效不丢失已提交事务。
- 所有写操作具备幂等键、乐观锁和审计事件；外部通知及同步采用可靠异步投递。
- 支持中文界面、无障碍基本要求、附件病毒扫描和全链路请求追踪。
- 在不少于 100,000 张工单的验收数据集上，授权后的团队队列和个人队列必须可遍历全部匹配记录；静态数据集逐页读取不得出现重复、漏项或不稳定排序。核心列表在默认 20 条和最大 100 条页大小下均满足 P95 小于 2 秒。
- 数据隔离自动化测试至少覆盖提单人、一线、二线、队列主管、服务经理、审计员和平台管理员，以及同组织、上下级组织、无关组织、跨组织协办和授权撤销场景；所有越权列表、详情、数量、导出和候选人读取均不得泄露对象存在性或汇总差异。

### 4.1 第一批 P0 验收标准

- 使用两个以上组织、三个以上团队队列和不少于 100,000 张工单的 MySQL 数据集验证；列表接口必须产生带数据库分页边界的查询，不得返回全量集合后由应用或浏览器截断。
- 相同主体、队列、筛选、排序和查询快照连续遍历时，每张未变化工单恰好出现一次；修改任一筛选条件后旧游标失效并返回明确的安全错误。
- 两名合资格人员并发领取同一团队未领取工单时仅一人成功；失败方获得“已被领取”的安全结果并刷新当前主办人，不产生双主办或重复完成任务。
- 一线支持不能查看未授权团队队列；队列主管不能越出其管理队列；服务经理和平台管理员没有数据范围时返回空的授权结果而非集团全量；审计员只能读取获授权范围且没有写动作。
- 跨组织协办获批后，协办人可查看并完成指定协办任务，但不能浏览来源组织队列或其他工单；协作失效或撤销后再次访问该对象被拒绝，历史操作仍可由有权审计主体追溯。
- 团队未领取、团队处理中、临近违约、已违约和待交接的数量与其下钻列表在同一快照和授权谓词下完全一致；任何子查询不可用时明确标记不可用，不以零值替代。

### 4.2 第二批 P0 验收标准

- 创建一个活动团队队列必须具有归属组织、至少一个已发布服务目录、一个活动成员和一个活动主管；任一范围为空、IAM 用户停用或目录越权时激活失败且不产生可领取队列。
- 普通成员可在其活动队列和对象范围内原子领取共享任务，但不能管理成员、范围或查看主管指标；队列主管可管理明确授权队列，不能读取第三方队列的数量、成员负荷或工单详情。
- 停用含未领取和在办工单的队列时必须先完成迁移预演；未领取任务迁移到已验证替代队列，在办任务保持责任与 SLA 连续，未配置替代队列或存在不可迁移任务时停用失败。
- 旧队列缺少可信归属组织、目录范围、活动成员或主管时进入 `MIGRATION_PENDING`，不接收新路由、不开放共享领取和主管工作台；既有在办工单保留责任快照并按当前对象权限处理，完成受审计映射和复核后才能激活新版本。
- 组织 A 与组织 B 各有同名已发布知识时，普通用户只看到当前 IAM 组织版本；组织为空、目录集合为空、目录无权或状态非已发布时，列表、详情、版本、预览、附件和反馈均不泄露记录存在性。
- 服务经理只有角色但没有目标组织 `DATA_SCOPE` 时，知识列表与审核队列为空且所有管理动作拒绝；同时具备角色和范围后，只能管理该组织及授权目录的知识。
- 从工单生成知识草稿时，归属组织与服务目录和源工单冻结快照完全一致；篡改请求体无效。导入知识的归属组织等于服务端当前 IAM 组织，越权或空目录被拒绝。
- 迁移前所有缺少 `owningOrganizationId` 或 `serviceCatalogItemIds` 的旧知识均不可普通检索、预览和审核；迁移后逐条保存映射依据、执行人、时间和校验结果，不得出现默认全局归属。

### 4.3 第三批 P0 验收标准

- 对创建队列、更新成员、激活和停用计划等每类写操作，使用同一 `Idempotency-Key` 和同一请求连续/并发提交至少两次，只产生一个业务对象和一组业务审计事件，并返回可关联的同一结果；同键异指纹返回 409 且无副作用。
- 停用含未领取、在办、版本冲突和越权工单的队列时，预演计划逐项列出迁移、交接和阻断结果；有阻断项的计划不能审批或执行，且不得泄露无权工单正文或人员信息。
- 审批后修改源队列、替代队列或任一任务版本，旧计划执行时必须转为已失效，不迁移任何新范围对象；重新执行必须创建新计划并重新审批。
- 执行过程中模拟在部分未领取任务迁移成功后发生服务中断；使用原执行幂等键重试时仅继续剩余/可重试失败项，成功项不重复迁移、通知或审计，最终逐项结果可完整追溯。
- 在办工单只生成交接清单，不直接改主办人或重置 SLA；全部计划项满足完成条件前，源队列不得显示为已完全停用。
- UI/API 联调验收必须能在请求超时后按计划 ID 查询真实状态，展示计划版本、审批、影响数量、逐项状态/原因和可重试标记；重复点击执行按钮不能产生第二次执行。

### 4.4 第四批 P0 验收标准

- 在业务迁移/交接结果已提交、幂等记录仍为 `IN_PROGRESS` 时强制终止执行进程；恢复后使用原键查询或重放，系统必须对账到既有结果、补记 `COMPLETED` 并返回原结果，不产生第二次业务事件、通知或审计。
- 两个应用节点同时观察到同一过期租约时，仅一个节点通过比较并交换取得新租约并继续剩余项；另一个节点返回当前 `IN_PROGRESS`。旧节点恢复后不能用旧令牌覆盖新状态或重复执行。
- 在幂等记录保留期内轮换 HMAC 密钥：轮换前创建的同键同请求仍返回原结果，异指纹仍返回 409；轮换后新请求使用新密钥版本。模拟旧密钥暂不可用时系统关闭式阻断并对账，不执行新副作用。
- 客户端在网络超时、`IN_PROGRESS` 和租约接管期间不得生成新键；自动化测试应证明换键按钮/重试逻辑不会被 UI 或 SDK 触发，状态查询不泄露 HMAC、正文或节点内部信息。

### 4.5 第五批 P0 验收标准

- 构造缺少 HMAC/keyVersion 但能以业务自然键和审计确认结果存在的历史记录，查询必须返回 `LEGACY_RESULT_ONLY` 和原结果安全引用；重放原写请求不能产生第二个对象、迁移、交接、通知或审计。
- 构造停在旧执行中且无法确认业务结果/租约的记录，查询返回 `RECONCILIATION_REQUIRED` 和人工处置引用；服务端和客户端均不得自动重试或生成新 key。
- 构造已确认无成功结果且不可安全恢复的历史记录，查询返回 `FAILED_FINAL` 和脱敏原因/受控新业务指引；只有用户明确发起新的业务意图才允许新 key。
- 人工对账完成后，原记录、证据和审计保持不可修改，只追加处置结论；无队列管理角色或 DATA_SCOPE 的人员不能读取或处置该记录。
- UI/SDK 对三种历史状态分别展示明确文案和下一步，均没有自动换 key 或强制重放入口；未知/他人 key 不泄露历史状态、结果引用或处置单存在性。

### 4.6 第六批 P0 验收标准

- 上传正常文件后先返回 `QUARANTINED`，扫描通过才转 `CLEAN`；在隔离期间直接调用下载、内联预览、知识预览/发布和案例匹配均被拒绝。
- 分别模拟恶意内容、扫描器超时和扫描器异常：恶意内容转 `REJECTED` 且无原文件重试能力；超时/异常转 `SCAN_FAILED` 且绝不返回下载链接或伪成功状态。
- 对 `SCAN_FAILED` 使用同一幂等键并发/重复提交扫描重试，仅创建一个有效扫描任务和一次业务审计；重试成功可转 `CLEAN`，再次失败仍为 `SCAN_FAILED` 并累加受控尝试次数。
- 达到最大次数、隔离文件哈希变化或扫描结果来源不可验证时，重试被阻断并进入人工处置；任何路径均不能通过改文件名、Content-Type、复制附件或客户端状态绕过。
- 文件从 `CLEAN` 被安全撤销/重新判定为非 CLEAN 后，已有下载/预览入口立即失效，知识发布和正文内联再次校验并拒绝。
- UI 验收覆盖四种状态、进度刷新、下一步提示、非 CLEAN 无下载/预览、仅可重试状态显示按钮，以及工单已创建但附件失败时不重复建单并能在原单恢复。

### 4.7 首批人性化 UX 验收标准

- 以提单人、一线、二线、队列主管、服务经理、审计员和平台管理员逐一登录，默认首页与角色矩阵 100% 一致；撤销队列关系/DATA_SCOPE 后刷新立即回退到仍授权视图，不保留失权偏好。
- 选取至少 5 个不同复杂度服务目录，用户均可在“选服务—填信息—确认”三个主步骤内完成；首次使用者任务成功率不低于 90%，中位建单时间不超过 3 分钟，除条件业务字段外不出现后台术语。
- 修改可持久化安全字段后 2 秒内生成绑定身份/组织/目录/版本的标签页草稿；刷新后恢复提示出现，选择恢复可还原当前版本仍兼容的系统、目录及非敏感结构化选项。身份切换、过期或主动放弃后不恢复；主题、自由正文、自定义标签、附件及文件名、令牌和 Blob/Base64 不进入持久化存储。
- 模拟表单版本升级，恢复提示列出版本变化和未兼容字段；系统不静默丢失、不提交隐藏字段，也不使用旧版本绕过服务端校验。
- 校验错误只在离开字段或尝试前进后出现，输入期间不抢焦点；提交含多个错误时页首摘要完整，首个可修复错误 100 毫秒内聚焦，所有错误可由键盘/读屏定位。
- 模拟主单创建成功后附件上传失败/扫描失败，页面只产生一个工单编号，可在原单恢复每个附件；刷新和重复点击不创建第二张工单。
- 在 375、768、1440 像素宽度和 200% 缩放下，以键盘完成选服务、填表、恢复草稿、添加/移除附件和提交；无导航死路、按钮遮挡或非表格必要横向滚动。
- 分别注入成功零数据、403、500、超时、超过新鲜度和单卡片失败：页面准确显示空/错/延迟/部分可用，保留旧数据时标明时间，绝不硬编码“平稳”、0、重大事件或班次；卡片数量与下钻同快照一致。

- 工单中心已提供固定个人队列：我的待办、逾期待办、今日完成、我已办、我发起的、草稿箱、我的待阅和所有可见工单。调用方只可提交固定队列码，不能提交任意人员、组织或处理组作为筛选条件。

- 已提供受控的“关联工单”读写能力：仅允许 `关联`、`重复于`、`父工单`、`关联问题`、`关联变更` 五类关系；创建时校验源单可修改、目标单可读，读取时逐条重新校验两端对象权限。关联不改变任何一张工单的状态、审批或 SLA，重复提交同一关系按自然键幂等，所有成功尝试均写入审计。
- 工作流主办/协办在领取、分派、转办和添加协办时固化 IAM 身份、组织、岗位与快照时间；详情仅返回当前有效协作关系，处理记录仍以历史事件留痕，人员后续调岗不会改写已捕获的责任事实。
